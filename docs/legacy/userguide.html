1. Running a Single Experiment

The simplest way to use ncsim is the headless CLI. No browser or server required — just a scenario YAML file and an output directory.

ncsim --scenario scenarios/demo_simple.yaml --output output/demo

Expected terminal output:

=== Simulation Complete ===
Scenario: Simple Demo
Scheduler: heft
Routing: direct
Interference: proximity
  radius=15.0
Seed: 42
Makespan: 3.001000 seconds
Total events: 7
Status: completed

You can override any scenario-level setting from the command line:

ncsim --scenario scenarios/demo_simple.yaml \
      --output output/demo-cpop \
      --scheduler cpop \
      --routing widest_path \
      --seed 123

2. Understanding Output Files

Each run produces three files in the output directory:

scenario.yaml

A copy of the input scenario with all defaults filled in. Useful for reproducing runs.

trace.jsonl

One JSON object per line for every discrete event in the simulation. Event types include:

Event TypeFieldsMeaning
task_start task_id, node_id, time A task began executing on a node
task_complete task_id, node_id, time A task finished executing
transfer_start edge_id, link_id, from_node, to_node, time A data transfer began on a link
transfer_complete edge_id, link_id, time A data transfer finished

metrics.json

Summary statistics including makespan, per-node utilization, per-link utilization, task-to-node assignments, scheduler and routing details, and (if applicable) WiFi RF configuration and carrier sensing range.

4. Scaling to Multiple Experiments

Bash Loop

for sched in heft cpop round_robin; do
  for seed in 1 2 3 4 5; do
    ncsim --scenario scenarios/parallel_spread.yaml \
          --output "output/sweep/${sched}_s${seed}" \
          --scheduler "$sched" --seed "$seed"
  done
done

Python Script

import subprocess, itertools

scenarios = ["demo_simple", "parallel_spread"]
schedulers = ["heft", "cpop"]

for scen, sched in itertools.product(scenarios, schedulers):
    subprocess.run([
        "ncsim",
        "--scenario", f"scenarios/{scen}.yaml",
        "--output", f"output/{scen}_{sched}",
        "--scheduler", sched,
    ], check=True)

5. Starting the Viz Platform

The GUI requires two running processes. See the Installation Guide §7 for full details.

# Terminal 1: Backend
cd viz/server && python run.py    # http://localhost:8000

# Terminal 2: Frontend
cd viz && npm run dev              # http://localhost:5173

Open http://localhost:5173 in your browser.

6. Home Page

The home page with two workflow entry points.

The home page presents two paths:

  • Configure & Run — Build a scenario from scratch using the form editor, then run it on the backend and visualize results immediately.
  • Visualize Existing — Browse saved experiments from the server's sample-runs/ directory, or load your own output files manually.

Clicking "Configure & Run" opens the experiment form. The form has five sections: basic configuration, interference model, network topology, DAG structure, and YAML preview.

7.4 Interference Model

CSMA/CA Bianchi model with WiFi RF configuration panel.

The interference dropdown selects one of four models (see §15 for full details):

  • None — No inter-link interference.
  • Proximity — Simple distance-based penalty. Shows a radius field.
  • CSMA/CA Clique — Static conflict graph model. Shows WiFi RF parameters.
  • CSMA/CA Bianchi — Dynamic SINR-aware model with Bianchi MAC throughput. Shows WiFi RF parameters.

When a WiFi model is selected, the RF Configuration panel appears with fields for transmit power, frequency, path loss exponent, noise floor, CCA threshold, channel width, WiFi standard, shadow fading, and RTS/CTS. See §16 for defaults and guidance.

7.5 YAML Preview

Auto-generated YAML reflecting all form settings.

At the bottom of the form, the Scenario YAML Preview section shows the YAML that will be sent to the backend. This updates live as you change any field. Click Copy to copy it to your clipboard — useful for saving as a reusable scenario file.

8. Running an Experiment

Running state with spinner indicator.

Click Run Experiment at the bottom of the form. The frontend POSTs the experiment name and scenario YAML to the backend's /api/run endpoint. The backend:

  1. Writes the YAML to a temporary directory
  2. Invokes ncsim --scenario ... --output ... as a subprocess
  3. Returns the scenario YAML, trace (JSONL), and metrics (JSON) as text

For simple scenarios this completes in under 2 seconds. Complex scenarios with many nodes, tasks, or WiFi interference may take longer.

9. Visualization Tabs

After a run completes (or after loading a saved experiment), the main view shows six tabs. Switch between them by clicking the tab bar or pressing keys 1–6.

9.1 Overview

Overview tab showing summary metrics.

The Overview tab presents a dashboard of key metrics:

  • Makespan — Total simulation time from first task start to last task completion.
  • Total tasks, transfers, events — Counts of simulation activity.
  • Per-node utilization — Bar chart showing what fraction of time each node was busy.
  • Per-link utilization — Bar chart showing link activity.
  • WiFi RF summary — Shown when a CSMA model was used.

9.2 Network

Network topology rendered with D3 force-directed layout.

Interactive D3 force-directed graph of the network topology. Nodes are sized proportional to compute capacity. Links are labeled with bandwidth. Pan by dragging the background, zoom with the scroll wheel.

9.3 DAG

DAG layout showing task dependencies with Dagre hierarchical positioning.

Dagre hierarchical layout of the task dependency graph. Each task node is colored by the compute node it was assigned to. Edges are labeled with data transfer sizes (MB).

9.4 Schedule

Gantt chart showing task execution and data transfer timelines.

Static Gantt chart with time on the x-axis and nodes on the y-axis. Task bars show execution periods, transfer bars show data movement between nodes. Hover for details.

9.5 Simulation

Animated simulation replay with network overlay and live Gantt chart.

The Simulation tab provides animated event replay. It combines:

  • Network overlay — Active nodes and links highlight in real time as tasks execute and data transfers occur.
  • Live Gantt chart — Bars grow as the simulation progresses.
  • Event log — Scrolling log of each event with timestamps. Click any event to jump to that point.
  • Playback controls — Play/pause, speed adjustment (0.5x–16x), step forward/backward, and jump to start/end.

9.6 Parameters

Parameters panel showing full configuration and task assignments.

Read-only inspector showing the complete scenario configuration: network definition (nodes and links), DAG structure (tasks and edges), scheduler, routing, interference model, RF parameters (if applicable), per-node task assignments, and utilization details.

10. Loading a Previous Run

Experiment browser showing saved runs.

From the home page, click Visualize Existing to open the experiment browser. This shows saved experiments from the server's viz/public/sample-runs/ directory. Each card shows the experiment name, scheduler, makespan, and task count.

Click any card to load it instantly — no backend needed since the files are already generated. You can also load results manually by providing your own scenario.yaml, trace.jsonl, and metrics.json files.

  name: "My Experiment"

  network:
    nodes:
      - id: n0
        compute_capacity: 100      # compute units per second
        position: {x: 0, y: 0}   # meters (for interference)
      - id: n1
        compute_capacity: 50
        position: {x: 10, y: 0}

    links:
      - id: l01
        from: n0
        to: n1
        bandwidth: 100             # MB/s
        latency: 0.001            # seconds

  dags:
    - id: dag_1
      inject_at: 0.0            # injection time (seconds)
      tasks:
        - id: T0
          compute_cost: 100      # compute units
          pinned_to: n0          # optional: force task to this node
        - id: T1
          compute_cost: 200
      edges:
        - from: T0
          to: T1
          data_size: 50          # MB

  config:
    scheduler: heft            # heft | cpop | round_robin
    seed: 42
    routing: direct            # direct | widest_path | shortest_path
    interference: proximity    # none | proximity | csma_clique | csma_bianchi

      noise_floor_dBm: -95

13. Scheduler Algorithms

AlgorithmStrategyWhen to Use
HEFT
heft		 Heterogeneous Earliest Finish Time. Ranks tasks by upward rank (longest path to exit in the DAG) and assigns each task to the node that gives the earliest finish time, accounting for computation and communication costs. Default choice. Best for heterogeneous networks where nodes have different capacities and link bandwidths vary.
CPOP
cpop		 Critical Path on a Processor. Identifies the critical path of the DAG and assigns critical-path tasks to the single fastest processor. Non-critical tasks are assigned with an EFT heuristic similar to HEFT. When the DAG has a clear critical path and one node is significantly faster than the rest.
Round Robin
round_robin		 Assigns tasks to nodes in cyclic order, ignoring compute capacities and data dependencies. Primarily useful as a baseline. Baseline comparisons and testing. Not recommended for production scheduling.

14. Routing Modes

ModeStrategyWhen to Use
Direct
direct		 Transfer data only on a direct link between source and destination. Fails if no direct link exists. Simple topologies where every communicating pair has a direct link.
Widest Path
widest_path		 Route through the path that maximizes the bottleneck bandwidth. Multi-hop transfers use intermediate nodes as relays. When maximizing transfer throughput matters more than hop count. Best for large data transfers.
Shortest Path
shortest_path		 Route through the fewest hops (unweighted). Uses intermediate nodes as relays. When minimizing latency (hop count) matters more than bandwidth. Good for small, latency-sensitive transfers.
Multi-hop routing is needed when the scheduler assigns communicating tasks to non-adjacent nodes. Without widest-path or shortest-path routing, the transfer will fail if no direct link exists. See the multihop_advantage.yaml scenario for a demonstration.

15. Interference Models

Interference models reduce the effective bandwidth of links when multiple nearby links are simultaneously active. This is applied on top of per-link fair sharing (N flows on one link each get bandwidth/N).

effective_bw = (base_bandwidth × interference_factor) / num_flows_on_link
ModelHow It WorksWhen to Use
None
none		 Factor = 1.0 always. No inter-link interference. Wired networks or when interference is not relevant.
Proximity
proximity		 Simple distance-based model. Links whose midpoints are within the configured radius contend with each other. Factor = 1/k where k is the number of simultaneously active contending links (including self). Quick approximation of wireless contention without WiFi-specific parameters.
CSMA/CA Clique
csma_clique		 Builds a conflict graph based on 802.11 carrier sensing rules and RF propagation. Links that can sense each other form cliques. Active links in the same clique share time equally: factor = 1/(clique members active). WiFi scenarios where you want conflict-graph contention without full SINR calculations.
CSMA/CA Bianchi
csma_bianchi		 Full WiFi model. Uses SINR from path-loss propagation to derive per-link MCS rates from the selected WiFi standard's rate table. Applies Bianchi's 802.11 DCF throughput model to compute MAC-layer efficiency based on the number of contending links. Realistic WiFi performance modeling with standard-specific MCS tables and MAC overhead.

16. WiFi RF Parameters

These parameters apply to the csma_clique and csma_bianchi models. They are specified under config.rf in YAML or in the WiFi RF Configuration panel in the GUI.

ParameterYAML KeyUnitDefaultDescription
TX Power tx_power_dBm dBm 20 Transmit power. Higher values extend range but increase interference.
Frequency freq_ghz GHz 5.0 Carrier frequency. 2.4 GHz has better range; 5 GHz has more bandwidth.
Path Loss Exponent path_loss_exponent — 3.0 Rate of signal attenuation with distance. 2.0 = free space, 3.0 = typical indoor, 4.0+ = dense environments.
Noise Floor noise_floor_dBm dBm −95 Background noise level. Affects SINR and achievable MCS rate.
CCA Threshold cca_threshold_dBm dBm −82 Clear Channel Assessment threshold. Links that can detect each other above this level are in the conflict graph.
Channel Width channel_width_mhz MHz 20 RF channel width. Wider channels = higher peak throughput but more interference. Options: 20, 40, 80, 160.
WiFi Standard wifi_standard — ax Determines MCS rate table for Bianchi model. Options: n (802.11n), ac (802.11ac), ax (802.11ax).
Shadow Fading shadow_fading_sigma dB 0 Standard deviation of log-normal shadow fading. 0 = deterministic propagation.
RTS/CTS rts_cts — false Enable RTS/CTS handshake. Extends the conflict graph to protect receivers from hidden terminals, at the cost of MAC overhead.
