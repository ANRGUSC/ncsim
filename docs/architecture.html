1. Overview

ncsim is a deterministic discrete-event simulator for networked computing research, paired with an interactive web-based visualization platform. Given a network topology and a task DAG described in YAML, the simulator schedules tasks onto nodes (using HEFT, CPOP, or round-robin), simulates execution and data transfers with bandwidth sharing and wireless interference, and produces a JSONL event trace and JSON metrics.

Same inputs + same seed = identical output, every time. The simulator is designed for reproducible experiments comparing scheduling algorithms, routing strategies, and interference models. The viz platform provides a browser-based UI for configuring scenarios, running simulations, and exploring results through interactive network topology views, DAG layouts, Gantt charts, and animated event replay.

4. Data Flow

  1. Load — ScenarioLoader reads the YAML file and produces a Scenario with Network, DAG(s), and Config.
  2. Configure — CLI overrides (seed, scheduler, routing, interference) are applied on top of the scenario config.
  3. Wire — Simulation is constructed with the network, a Scheduler, a DAGSource, a RoutingModel, and an optional InterferenceModel.
  4. Inject — DAGs are injected at their inject_at times as DAG_INJECT events. The scheduler's on_dag_inject() returns a PlacementPlan.
  5. Execute — The event loop pops events from the priority queue. The engine handles each event type, updating node/link state and scheduling follow-on events.
  6. Trace — Each processed event is forwarded to the TraceWriter, which appends a JSON line to trace.jsonl.
  7. Results — After the queue is empty, makespan and utilization metrics are written to metrics.json.

5. Key Abstractions

7. Scenario YAML Format

scenario:
  name: "My Experiment"

  network:
    nodes:
      - id: n0
        compute_capacity: 100      # compute_units/second
        position: {x: 0, y: 0}  # for visualization & interference
      - id: n1
        compute_capacity: 50
        position: {x: 10, y: 0}

    links:
      - id: l01
        from: n0                   # directional: n0 → n1
        to: n1
        bandwidth: 100             # MB/second
        latency: 0.001            # seconds

  dags:
    - id: dag_1
      inject_at: 0.0             # simulation time to inject
      tasks:
        - id: T0
          compute_cost: 100       # compute_units (runtime = cost / capacity)
        - id: T1
          compute_cost: 200
          pinned_to: n1            # optional: force assignment to this node
      edges:
        - from: T0
          to: T1
          data_size: 50           # MB to transfer

  config:
    scheduler: heft             # heft | cpop | round_robin
    seed: 42
    routing: direct             # direct | widest_path | shortest_path
    interference: proximity      # none | proximity | csma_clique | csma_bianchi
    interference_radius: 15.0   # for proximity model (default: 15.0)
    rf:                          # optional: 802.11 RF parameters (for csma_* models)
      tx_power_dBm: 20          # transmit power (dBm)
      freq_ghz: 5.0              # carrier frequency (GHz)
      path_loss_exponent: 3.0   # n (2=free space, 3-4=indoor)
      noise_floor_dBm: -95      # receiver noise floor (dBm)
      cca_threshold_dBm: -82    # clear channel assessment threshold (dBm)
      channel_width_mhz: 20     # 20 | 40 | 80 | 160
      wifi_standard: "ax"       # "n" | "ac" | "ax" (selects MCS table)
      shadow_fading_sigma: 0.0  # 0 = deterministic, >0 = log-normal std dev (dB)
      rts_cts: false             # extend conflict graph to protect receivers
WiFi link bandwidth: When using csma_clique or csma_bianchi, links without an explicit bandwidth field derive their rate from RF parameters (distance → SNR → MCS → MB/s). Links with explicit bandwidth keep their specified value, allowing wired and wireless links in the same scenario.

9. Simulation Models

9.1 Compute Time

task_runtime = compute_cost / node.compute_capacity

Each node runs at most one task at a time (single-server FIFO queue). No preemption.

9.2 Transfer Time

transfer_time = (data_size / effective_bandwidth) + total_latency

For multi-hop paths, total_latency is the sum of all link latencies (store-and-forward), and effective_bandwidth is the bottleneck across all links after sharing and interference.

9.3 Bandwidth Sharing (Per-Link)

If N transfers share a link simultaneously, each gets base_bandwidth / N. When a transfer starts or completes, all co-resident transfers are recalculated with updated completion times.

9.4 Inter-Link Interference

Orthogonal to per-link sharing. Reduces a link's base bandwidth when nearby links are active.

effective_per_flow = (link.bandwidth × interference_factor) / num_flows_on_link
ModelClassBehavior
noneNoInterferenceAlways returns factor 1.0. No cross-link effects.
proximityProximityInterference(radius)Counts k active links within radius of midpoint. Factor = 1/k.
csma_cliqueCsmaCliqueInterferenceStatic: link.bandwidth = PHY_rate / max_clique_size at setup. Factor = 1.0 always. See WiFi Model.
csma_bianchiCsmaBianchiInterferenceDynamic: separates CSMA contention (Bianchi η(n)/n) from hidden terminal SINR degradation. See WiFi Model.

9.4.1 802.11 WiFi Link & Interference Model

The WiFi model (csma_clique and csma_bianchi) replaces manually specified link bandwidths with physically-grounded rates derived from RF parameters, node positions, and IEEE 802.11 MCS tables. It is defined in models/wifi.py and models/interference.py.

For full mathematical details, see docs/wifi_interference_model.tex.

9.4.2 Path Loss & Received Power

Log-distance path loss with Friis free-space reference at d0 = 1m:

PL(d0) = 20 · log10(4π · d0 · f / c)
PL(d) = PL(d0) + 10 · n · log10(d / d0)
Prx(d) = Ptx − PL(d) − XSF

where XSF is the shadow fading component (0 by default). SNR = Prx − N0.

9.4.3 MCS Rate Adaptation

SNR selects the highest MCS whose minimum threshold is met from IEEE 802.11n/ac/ax tables (1 spatial stream, 20 MHz base). Rates scale linearly with channel width.

StandardMCS RangePeak Rate (20 MHz)Modulation Range
802.11n0–765.0 MbpsBPSK–64-QAM
802.11ac0–986.7 MbpsBPSK–256-QAM
802.11ax0–11143.4 MbpsBPSK–1024-QAM

If SNR < 5 dB (below MCS 0 threshold), the link is not viable (rate = 0). Rates are converted to MB/s: rate_MBps = rate_Mbps / 8.

9.4.4 Conflict Graph

The conflict graph determines which links cannot transmit simultaneously under CSMA. Carrier sensing range: dCS = d0 · 10(Ptx − θCCA − PL(d0)) / (10n).

Without RTS/CTS: Two links conflict if either transmitter can sense any node of the other link (distance ≤ dCS).

With RTS/CTS: Two links conflict if any node of one link can sense any node of the other link. This extends the conflict zone to protect receivers.

Max clique sizes are computed per-link using Bron-Kerbosch (exact, ≤50 links) or greedy approximation.

9.4.5 Bianchi MAC Efficiency

Bianchi's saturation throughput model (IEEE JSAC, 2000) gives the MAC efficiency η(n) for n contending stations. Solves coupled equations for transmission probability τ and collision probability p:

τ = 2(1−2p) / [(1−2p)(W+1) + pW(1−(2p)m)]
p = 1 − (1−τ)n−1

where W = 16 (CWmin) and m = 6 (max backoff stage). Efficiency:

η(n) = Psuccess · Tsuccess / E[Tslot]

Properties: η(1) = 1.0, monotonically decreasing, always positive. Typical: η(2) ≈ 0.88, η(10) ≈ 0.59.

9.4.6 CSMA Clique Model

Static model: all contention effects baked into link bandwidth at setup time.

link.bandwidth = PHY_rate / ω(ℓ)
interference_factor = 1.0 (always)

where ω(ℓ) is the max clique size containing link ℓ. Conservative worst-case bound. No dynamic recalculation needed.

9.4.7 CSMA Bianchi Model

Dynamic model that correctly separates two interference mechanisms:

  1. Contention domain (conflict graph neighbors): CSMA prevents simultaneous TX. These links share airtime: each of n contending links gets η(n)/n of the channel.
  2. Hidden terminals (active links not in conflict graph): May transmit simultaneously, causing SINR degradation at the receiver.
link.bandwidth = PHY_rate (base SNR-only rate)
factor = (RSINR / Rbase) · (η(n) / n)

where RSINR accounts for hidden terminal interference only (SINR from interfering transmitters → MCS lookup), and n = 1 + |active contending neighbors|. If no hidden terminals are active, RSINR/Rbase = 1.0. When a transfer starts/completes, all active conflict graph neighbors are recalculated.

Key insight: CSMA prevents simultaneous transmission within the contention domain, so contending links affect throughput via time-sharing (η(n)/n), not via SINR degradation. Only hidden terminals (outside the conflict graph) contribute to SINR reduction.

9.4.8 Shadow Fading

Optional log-normal shadow fading (Gaussian in dB domain). Per-node-pair, symmetric, deterministic from seed. Configured via shadow_fading_sigma in the rf: section. Default 0.0 (no fading).

9.6 Event Ordering & Determinism

Events are ordered by a three-level key:

(round(sim_time, 6), event_type.priority, event_id)

All times are rounded to microsecond precision (6 decimal places). Event types have fixed priorities:

Event TypePriorityDescription
DAG_INJECT0New DAG arrives
TASK_COMPLETE1Task finishes execution
TRANSFER_COMPLETE2Data transfer finishes
TASK_READY3Task ready to execute
TASK_START4Task begins execution
TRANSFER_START5Data transfer begins

Same inputs + same seed = identical event sequence. The event_id (monotonic counter) breaks ties for insertion-order FIFO at the same time and priority.

11.3 Data Flow

  1. Configure — The user builds a scenario via the ExperimentForm UI (topology presets, DAG presets, scheduler/routing/interference settings) or loads a saved run from public/sample-runs/.
  2. Run — The frontend POSTs the experiment name and scenario YAML to /api/run. The backend writes the YAML to a temp directory, invokes python -m ncsim --scenario ... --output ... as a subprocess, and returns the scenario.yaml, trace.jsonl, and metrics.json contents.
  3. Parse — Frontend loaders (scenarioLoader, traceLoader, metricsLoader) parse the raw text into typed TypeScript objects.
  4. Visualize — The parsed data flows into six visualization tabs, each rendering a different aspect of the simulation results.
